# grill-with-docs

> 一次无休止的访谈，用来打磨计划或设计——同时边问边产出文档（ADR 和术语表）。

## 1. 一句话理解

`grill-with-docs` 是**一个组合命令**：跑一轮 `/grilling` 拷问，同时挂上 `/domain-modeling`，让每一个敲定的术语和决策当场落成 `CONTEXT.md` 和 ADR，而不是只停留在对话里。

## 2. 它解决什么问题

`grilling` 能把模糊计划追问成共同理解，但它本身不落盘——问完了，术语和决策可能随对话消失。`grill-with-docs` 补上这一半：在项目仓库里留下可复用的上下文（术语表 + 决策记录），让这次访谈的成果能被后续 session 读到。

## 3. 核心心智模型

**"拷问"和"建模"是同一件事的两面。** 拷问负责把问题逼出来、把选择摆到用户面前；建模负责把敲定的结果固化。两者交替，不是先问完再一次性写文档。术语一敲定 → 写 `CONTEXT.md`；出现难以逆转且需上下文、经过权衡的决策 → 写 ADR。

## 4. 一次典型运转

在代码仓库里澄清一个还不确定的功能：

1. 起 `/grilling` 会话，一轮一轮问设计树的前沿问题，每个问题附推荐答案。
2. 每当一个术语被精确定义（比如"cancellation"到底指什么），立即用 `/domain-modeling` 写进 `CONTEXT.md`。
3. 每当出现一个真正的、不可逆的权衡决策，写一条 ADR。
4. 直到前沿为空——所有分支都访问过、没有静默假设——才停下来。

## 5. 何时用 / 何时不用

**用**：在**有代码仓库**、想把澄清的成果（术语 + 决策）留在项目文档里的场景。

**不用**：
- 没有仓库、只想打磨一个方案 → 用 `grill-me`（纯访谈，不写文件）。
- 只需要一次性澄清、不值得留文档 → 用 `grilling`。

## 6. 依赖与网络位置

- 依赖 `grilling`（对话原语）和 `domain-modeling`（写文档）。
- 是 `ask-matt` 主交付路径的第一步（有仓库时澄清目标）。

## 7. 易错点与坑

- **只问不记**：那等于 `grilling`，浪费了本 skill 的存在意义。
- **记太杂**：`CONTEXT.md` 只记术语，别塞实现细节；ADR 只记符合三条标准的决策。
- **问完再补文档**：要边问边写，不是收尾批量补。
