# domain-modeling

> 在设计中主动构建并打磨项目的领域模型：挑战术语、发明边界场景、把词汇和决策写进 `CONTEXT.md` 与 ADR。

## 1. 一句话理解

`domain-modeling` 是**主动的**领域建模纪律——不是读 `CONTEXT.md` 查词汇（那只是一行习惯），而是在你**改变模型**时：当术语被敲定、边界被澄清，当场写进 `CONTEXT.md`；当出现难以逆转的决策，才写 ADR。

## 2. 它解决什么问题

代码和产品里，模糊/过载的术语（"account 是指 Customer 还是 User？"）、代码与说法不一致（"你说支持部分取消，但代码只取消整单"）、以及"为什么当初这么决定"的丢失，都会让团队和 agent 越做越乱。`domain-modeling` 把这些在发生的那一刻就地收敛，而不是事后补。

## 3. 核心心智模型

**`CONTEXT.md` 是术语表，别的什么都不是。** 它必须完全不含实现细节，不是 spec、不是草稿、不是实现决策库。它的唯一职责：一个词、一个精确定义。

**ADR 要"吝啬"地给。** 只有三条同时成立才写 ADR：

1. **难以逆转**——改主意代价真实存在；
2. **没有上下文会令人惊讶**——未来读者会问"为什么这么做？"；
3. **真正的权衡结果**——确实有多个备选、你为特定理由选了一个。

缺任何一条就跳过。ADRs 记录的是决策，不是过程记录。

## 4. 一次典型运转

会话中讨论订单取消：

1. **对照术语表挑战**："你的 glossary 把 'cancellation' 定义为 X，但你现在似乎指 Y——到底是哪个？"
2. **打磨模糊语言**："你说 'account'，指 Customer 还是 User？这俩是不同的东西。"
3. **用具体场景压测**：发明边界场景逼用户说清概念边界。
4. **与代码交叉核对**："你的代码取消整张 Order，但你说可以部分取消——哪个对？"
5. **术语一敲定就写进 `CONTEXT.md`**，不批量补。
6. 如果这是个难以逆转、需要上下文、又经过权衡的决策，才提议写 ADR。

## 5. 何时用 / 何时不用

**用**：讨论代码库术语、写/改 `CONTEXT.md`、记录/编辑 ADR。

**不用**：只是读 `CONTEXT.md` 查词——那是任何 skill 都能做的一行习惯，不是本 skill。

## 6. 依赖与网络位置

- 常与 `grilling` 合跑（边问边固化术语），也是 `grill-with-docs`、`triage`、`wayfinder`、`improve-codebase-architecture` 的内置环节。
- 附属：`CONTEXT-FORMAT.md`、`ADR-FORMAT.md`。
- 与 `codebase-design` 分工：前者管领域词汇与不可逆决策，后者管模块/接口/接缝等代码结构语言。

## 7. 易错点与坑

- **把 `CONTEXT.md` 当 spec 或草稿**：它会立刻被实现细节污染，失去"术语表"的纯粹性。
- **ADR 泛滥**：三条标准缺一即不写；"记录一下"不等于该有 ADR。
- **术语批量补**：要当场写，别攒着——那一刻的精确语境稍纵即逝。
