# codebase-design

> 设计"深模块"（deep module）的共享词汇表：用一套精确术语讨论模块、接口、深度、接缝、适配器，以及如何靠深度换取杠杆与局部性。

## 1. 一句话理解

`codebase-design` 是一份**词汇表 + 原则集**，教你把代码设计成"深模块"——小接口背后藏大量行为，放在干净的接缝处，通过接口可测试。它的核心价值是**统一的语言**：这些词要原样使用，不许替换成"组件/服务/API/边界"。

## 2. 它解决什么问题

设计接口时，人和 agent 最容易犯的错是**语言漂移**——一会儿说"组件"、一会儿说"服务"、一会儿说"边界"，同一个概念多个名字，讨论就失焦。更根本的是，缺少"深度"这个度量，人就容易设计出**浅模块**：接口几乎和实现一样复杂，调用者什么都没省下。`codebase-design` 同时解决这两件事：给术语，给度量。

## 3. 核心心智模型

**深度 = 杠杆（leverage），而不是实现行数/接口行数之比。** 一个模块"深"，指的是调用者每学一点接口，能驱动的行为很多；"浅"则是接口几乎和实现一样复杂。这一条明确拒绝了 Ousterhout 的"行数比"框架（那会奖励注水实现）。

支撑它的关键概念：

- **接缝（seam）**：你能不改动某处就改变行为的地方，是模块接口所在的位置。放哪条接缝本身就是一个独立设计决策。
- **适配器（adapter）**：在接缝处满足接口的具体东西，描述的是**角色**（填哪个槽），不是内部是什么。
- **删除测试**：想象删掉这个模块——复杂度消失（它是个空壳）还是重新散落到 N 个调用者（它在挣口粮）？
- **接口就是测试面**：调用者和测试穿过同一条接缝。想测"接口之后"的东西，说明模块形状错了。
- **一个适配器 = 假想的接缝；两个适配器 = 真的接缝**：除非有东西真的跨接缝变化，否则别引入它。

## 4. 一次典型运转

设计一个模块接口时：

1. 先问三个问题：能不能减少方法数？能不能简化参数？能不能把更多复杂度藏进实现？
2. 用"删除测试"检验它是不是浅模块（空壳）。
3. 检查可测试性三条：接受依赖而非创建依赖（`processOrder(order, gateway)` 而非内部 `new StripeGateway()`）；返回结果而非产生副作用；小表面积。
4. 若接缝位置、接口形状本身有疑问，用 `design-it-twice` 模式并行出几个截然不同的接口方案，按深度/局部性/接缝位置比较。

## 5. 何时用 / 何时不用

**用**：设计或改进模块接口、找"深化"机会、决定接缝位置、让代码更可测或更易被 AI 导航；以及其他 skill 需要这套深模块词汇时。

**不用**：纯领域词汇（那归 `domain-modeling`）；只做评审不重设计（那归 `code-review`）。

## 6. 依赖与网络位置

- 附属文件：`DEEPENING.md`（深化一个簇）、`DESIGN-IT-TWICE.md`（并行设计接口）。

## 7. 易错点与坑

- **替换术语**："component/service/API/boundary" 是被明确拒绝的说法——语言一致性本身就是目的。
- **把 `interface` 理解窄了**：它不是 TS 的 `interface` 关键字，而是调用者需要知道的一切（签名 + 不变量 + 顺序约束 + 错误模式 + 配置 + 性能）。
- **为一个还没变的东西接缝**：一个适配器只是假想接缝，别为了"将来可能"而引入。
