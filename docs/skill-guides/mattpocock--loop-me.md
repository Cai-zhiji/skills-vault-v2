# loop-me

> 拷问我关于"我要构建的工作流"的 spec，在本工作区内——唯一的产出是工作流 spec。

## 1. 一句话理解

`loop-me` 跑一场有状态的 `/grilling` 会话，但**只产出工作流 spec**：用无休止的拷问纪律，围绕"loop/workflow"这组词汇与目标，边问边建、改、删 `workflows/*.md` 里的 spec。

## 2. 它解决什么问题

用户生活里有很多可预测、可委托的重复模式（loop），但"要不要自动化、怎么自动化、哪里需要人"往往没想清。`loop-me` 用拷问把这些 loop 收敛成"实现者能不问一句就建出来"的 spec。

## 3. 核心心智模型

**Loop 透镜**：一个 loop 是用户生活中反复出现的模式（职业、一周、早晨、单个活动）。把生活看成"环中环"能揭示它的可预测性——而可预测才值得委托。用它找出值得 spec 的 loop，并主动提议用户没注意到的。

**一组只在需要时启用的词汇**（**不强制任何结构**，除非拷问表明需要）：

- **Trigger**：什么触发每次运行——事件（新邮件/新 issue）或排程（每天早晨）。事件触发通常更高效。
- **Checkpoint**：人参与验证/决定的一个点。有的工作流没有、全自动；有的根本不用 AI。
- **Push right**：把 checkpoint 尽量往后推——在人介入前做完最多的工作，让人一次、晚一点、带着准备好的东西被问。
- **Brief**：checkpoint 呈现的东西——紧凑、决策就绪的摘要（产出了什么、为什么、链到资产），不是原始输出。用户读 brief 不读草稿，审阅速度优先。

**Definition of done**：一个实现者 agent 能不问一句就建出这个工作流。拷问到没有遗留问题为止。

## 4. 一次典型运转

1. `NOTES.md` 空/薄就先访谈用户的世界（用的工具、处理的渠道、他自己的术语）。
2. 用 loop 透镜找出值得 spec 的 loop，拷问 trigger/checkpoint/是否需要 AI。
3. 边问边把 spec 写进 `workflows/*.md`。
4. 直到实现者能不问一句就建出来。

## 5. 何时用 / 何时不用

**用**：想设计/澄清某个要反复运行的工作流时。

**不用**：一次性任务（不值得 spec 成 loop）。

## 6. 依赖与网络位置

- 依赖 `grilling`（拷问纪律）。
- 是 mattpocock in-progress 中偏"个人生产力自动化"的一块。

## 7. 易错点与坑

- **强制加结构**：没有 AI、没有 checkpoint、没有排程，只要拷问没证明需要就别加。
- **checkpoint 太早**：要 push right，尽量晚地、一次性地问人。
- **给用户看原始输出**：checkpoint 呈现 brief（决策就绪摘要），不是草稿。
