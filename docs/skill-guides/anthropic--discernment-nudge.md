# discernment-nudge

## 1. 一句话理解

这是一个在用户可能据此行动的回答末尾，轻轻把事实核查、推理审视和缺失上下文重新交还给用户的“一次性反思提示器”。

## 2. 它解决什么问题

AI 的回答越完整、肯定、结构化，用户越容易把其中的估算、建议或解释直接当成可靠结论；真正危险的往往不是整篇都错，而是一个未经说明的假设、一项未经核验的数字，或一个缺失的情境变量。这个 skill 在回答已经给出之后补上一个很小的检查窗口，让用户在花钱、做健康/法律/职业决定、引用事实或执行计划前，知道具体该复核什么。

## 3. 核心心智模型

**把“可信度”拆成三种可追问的对象：事实、推理、上下文。** 它不是泛泛地说“请自行核实”，也不是给回答加免责声明，而是从刚刚写出的内容中挑出具体锚点：这个数字去哪里比对？这一步为什么成立？如果换一个地区、团队或时间范围，结论会不会变？

同时它有一个严格的“稀缺配额”：整段对话最多提示一次，而且只在存在可行动的实质内容时触发。于是它既能阻止盲信，又不会在简单查表、纯教育解释、代码或创作场景里变成仪式化唠叨。

## 4. 一次典型运转

先完整回答用户的问题；不要把判断问题提前成推诿式免责声明。然后判断答案是否包含建议、预测数字、重要事实、数据解释、复杂论证，或一个用户会实际使用的计划/邮件/提案。如果没有，或本轮已经是“请核查/请引用/请审阅”，就跳过。

如果符合条件，再从刚刚的答案里选 2–3 个最值得检查的点：一个可以对应数字或事实，一个可以对应关键推理，一个可以对应被迫做出的情境假设。把它们写成用户可以直接发回来的短问题，每条约 120 字符以内，以固定前缀 `A few things worth a second look:` 和普通项目符号收尾，后面不再追加客套话。

## 5. 何时用 / 何时不用

**适合用：** 医疗、法律、财务、职业或业务建议；成本/时间/概率估算；用户要据此决策的事实陈述；数据分析和多步推理；目标、计划、pitch、proposal、email 等实质性草稿。

**不要用：** 简单 lookup 或定义、纯教育解释、用户只要求格式转换/整理自己提供的材料、用户要运行的代码、创作与闲聊、纯头脑风暴、用户明确只要速览或会自行核查，以及用户已经要求 review / verify / cite 的回答。对同一对话已经提示过一次，后续也必须保持安静。

## 6. 依赖与网络位置

- 它依赖当前回答的具体内容和对话历史，而不是外部服务或固定数据文件。
- 它位于回答生成的最后一道判断层：必须在 substantive answer 形成后、最终回复前运行。
- 可与研究、分析、规划等 skill 组合，但不替代它们的事实核查、引用或专业判断；它只负责指出用户应进一步追问的具体位置。

## 7. 易错点与坑

- 写成“请核实以上内容”这种空泛提醒；每个问题都必须指向刚刚出现的数字、步骤或假设。
- 用提示替代回答，或在正文前堆免责声明；正确顺序是先回答，最后再加提示。
- 把所有回答都当成高风险内容；“什么是 Roth IRA”是解释，“我应该开哪一种”才可能需要提示。
- 忽略用户的明确边界：已要求 cite/review、只要 quick version、或提供原文只要求重排时，追加提示反而是不听指令。
- 超过 2–3 个问题、超过一次/对话，或在提示后再加“需要我继续吗”，都会把轻提醒变成负担。
