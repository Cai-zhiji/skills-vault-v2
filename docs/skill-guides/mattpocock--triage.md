# triage

> 让 issue 和外部 PR 走过一个 triage 角色状态机：分类、核实、必要时拷问，最后写出 agent 就绪的简报。

## 1. 一句话理解

`triage` 是一台**状态机**：把 issue（以及外部 PR——"PR 是带代码的 issue"）从一个未处理状态，推进到 `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`，中间核实主张、必要时拷问澄清。

## 2. 它解决什么问题

外部反馈（bug、功能请求）是乱的：没分类、缺信息、没验证、agent 接不了。`triage` 把它整理成"agent 能直接拿走的 brief"，或明确打回要信息、或判 `wontfix` 关闭。

## 3. 核心心智模型

**两个分类角色 + 五个状态角色**，每个 issue 恰好各带一个：

- 分类：`bug` / `enhancement`。
- 状态：`needs-triage` → `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`。

**核实（verify）先于拷问。** 写 agent brief 之前，先验证主张成立：bug 要按报告步骤复现，PR 要 checkout 跑测试确认 diff 做它声称的事。核实过的主张才能产出强 brief。

**两条冗余/拒绝检查**：查代码库是否已实现该行为（按领域概念搜，不只是措辞），以及 `.out-of-scope/` 是否已有类似被拒请求。已实现 → `wontfix`（已实现，不写 out-of-scope）；已拒绝的增强 → 写 `.out-of-scope/`。

**所有 AI 发出的评论都要带免责声明**：`> *This was generated by AI during triage.*`

## 4. 一次典型运转

1. 收集上下文（读 issue/PR 全文、解析旧 triage notes、探索代码库、跑冗余+拒绝检查）。
2. 推荐分类/状态 + 理由，等维护者方向。
3. 核实主张（复现 bug / 跑 PR 测试）。
4. 需要就拷问（`grilling` + `domain-modeling`）。
5. 落地：`ready-for-agent` 写 agent brief；`needs-info` 写 triage notes；`wontfix` 按原因关闭（已实现/拒绝 bug/拒绝增强）。

## 5. 何时用 / 何时不用

**用**：维护者想让外部 issue/PR 被整理成可执行、或指定 "move #42 to ready-for-agent"。

**不用**：`to-tickets` 产物已可直接实现，不必再过 triage；内部在飞 PR（协作者的）不是 triage 对象。

## 6. 依赖与网络位置

- 内部用 `grilling` + `domain-modeling`。
- 附属：`AGENT-BRIEF.md`、`OUT-OF-SCOPE.md`。

## 7. 易错点与坑

- **把已实现的东西写进 `.out-of-scope/`**：那是给"被拒绝"的，已实现的只指向它所在位置。
- **不核实就拷问/写 brief**：核实是写强 brief 的前提。
- **忘免责声明**：所有 triage 期间发的评论都要带 AI 生成声明。
- **重问已解决的问题**：先读旧 triage notes，别重复问。
