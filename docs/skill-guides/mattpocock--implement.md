# implement

> 基于 spec 或一组 ticket 实现一块工作：用 TDD 在预定的接缝处逐步实现，最后自审。

## 1. 一句话理解

`implement` 是一条极简的执行纪律：按 spec/ticket 实现 → 尽量用 `/tdd` 在**预先约定好的接缝**处写 → 定期类型检查、单测，最后跑全量测试 → 用 `/code-review` 自审 → 提交到当前分支。

## 2. 它解决什么问题

"实现"看似简单，但最容易出问题的是**节奏**：要么一头扎进去写到天荒地老才发现跑偏，要么从不验证。`implement` 用几条硬约定钉住节奏——测试先行、定期 typecheck、收尾全量测试、完成后自审——让实现过程可控可验证。

## 3. 核心心智模型

**在预定的接缝处写测试。** 这不是凭空测试，而是"先在 `tdd` 的语义里确认要测哪些公共边界（seam），再动手"。实现围绕这些接缝推进，而不是对着内部实现细节堆测试。

## 4. 一次典型运转

1. 读 spec/ticket，理解要交付的端到端行为。
2. 与用户确认接缝（如果还没定）。
3. 用 `tdd` 红→绿循环：一个测试、一个最小实现，逐片推进。
4. 定期跑单测文件和类型检查；最后跑一次全量测试套件。
5. 用 `code-review` 从标准 + 规格两条轴自审一遍。
6. 提交到当前分支。

## 5. 何时用 / 何时不用

**用**：有一份 spec 或 ticket 要落地实现时。

**不用**：还没有规格/任务、还在澄清阶段（先 `grill-with-docs`/`to-spec`）；纯诊断 bug（`diagnosing-bugs`）。

## 6. 依赖与网络位置

- 依赖 `tdd`（实现方式）、`code-review`（收尾自审）。
- 是 `ask-matt` 交付链的末端、`to-tickets` 产物的消费方。

## 7. 易错点与坑

- **跳过收尾全量测试**：单测过不代表整体没坏，最后必须跑一次全量。
- **不预确认接缝就写测试**：`tdd` 的核心约束是"只在预先约定的接缝处测试"。
- **实现完不自审**：`code-review` 是流程的一部分，不是可选项。
