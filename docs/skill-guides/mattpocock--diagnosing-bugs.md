# diagnosing-bugs

> 一套诊断硬 bug 与性能回归的纪律：先建一个能变红的紧反馈回路，再复现/最小化、假设、打点、修复加回归测试、收尾复盘。

## 1. 一句话理解

`diagnosing-bugs` 的整个核心只有一句：**在有任何理论之前，先建一个对"这个 bug"会变红的紧反馈回路**。剩下的五个阶段（复现最小化 → 假设 → 打点 → 修复+回归测试 → 复盘）全都是围绕这个回路展开的机械动作。

## 2. 它解决什么问题

人 debug 最常见的失败是**直接读代码猜**：还没办法稳定复现，就开始想"是不是这里的问题"。这是这个 skill 明确要阻止的——"没有变红回路，就别进 Phase 2"。它把 debug 从玄学变成工程。

## 3. 核心心智模型

**紧（tight）且能变红（red-capable）的反馈回路 = 90% 的工作。** 一个合格的回路要同时满足：

- **能变红**：它驱动真实的 bug 代码路径，并断言用户的**确切症状**，所以能在这个 bug 上变红、修好变绿——不是"跑起来没报错"。
- **确定性**：每次跑结果一致（flaky bug 则要一个钉住的高复现率）。
- **快**：秒级，不是分钟级。
- **agent 可跑**：无人值守可跑；只有走 HITL 脚本才需要人在回路里。

**名字是第二个要点**：一切 debug 日志都要带唯一前缀（如 `[DEBUG-a4f2]`），收尾时一次 `grep` 清干净；没打 tag 的日志会活下来，打了 tag 的会死。

## 4. 一次典型运转

收到"接口偶发超时"：

1. **Phase 1 建回路**：按顺序试——失败测试 → curl 脚本 → CLI 快照比对 → 无头浏览器 → 重放抓包 → 一次性 harness → property/fuzz → bisection → 差分 → HITL。建出来就**收紧**：更快、信号更锐、更确定。
2. **Phase 2 复现+最小化**：跑回路看它变红，确认是用户描述的那个失败；然后逐个砍输入/调用者/配置/数据，砍到"每个剩余元素都不可再删"。
3. **Phase 3 假设**：生成 3–5 条**可证伪**假设（"如果 X 是原因，改 Y 会消失/改 Z 会变糟"），先给用户看排名（他们常有领域知识重排）。
4. **Phase 4 打点**：每个探针对应 Phase 3 的具体预测，一次只改一个变量；性能回归别用日志，先测基线再二分。
5. **Phase 5 修复+回归测试**：在**正确的接缝**处先写回归测试（浅接缝会给人虚假信心）；没有正确接缝本身就是发现，记下来交给架构。
6. **Phase 6 收尾**：重跑原回路、回归测试过、清掉 `[DEBUG-*]`、删 throwaway、把正确假设写进 commit message，再问"什么能预防这个 bug"。

## 5. 何时用 / 何时不用

**用**：用户说"diagnose/debug this"，或报告东西坏了/抛错/失败/变慢。

**不用**：还没确定"有 bug"的泛泛代码改进；简单一眼就能定位的 bug。

## 6. 依赖与网络位置

- 结束时若发现是架构问题（没有好测试接缝、耦合），交接给 `improve-codebase-architecture`。
- 读 `CONTEXT.md` 建立模块心智模型、看相关 ADR。
- 附属：`scripts/hitl-loop.template.sh`（人类在回路时用）。

## 7. 易错点与坑

- **没回路就猜**：这是它要根除的头号反模式——"red-capable command 不存在，就别进 Phase 2"。
- **建不出回路硬撑**：要明确停下、列出试过什么、向用户要复现环境/脱敏抓包/生产打点许可。
- **误判"变红"**：回路复现的必须是用户描述的失败，不是碰巧在附近的另一个失败——错 bug = 错修。
- **日志忘了 tag**：收尾清不掉。
