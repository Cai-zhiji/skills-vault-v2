# prototype

> 建一个一次性原型来回答一个设计问题：状态模型/逻辑对不对，或者 UI 长什么样。

## 1. 一句话理解

`prototype` 是**用 throwaway 代码回答问题**：先辨清你在回答哪个问题（逻辑/状态模型 vs UI 外观），再走对应的两条分支之一，产出能立刻跑、跑完即弃的东西。

## 2. 它解决什么问题

有些设计问题光靠讨论永远说不清——状态机在纸上推不动、UI 长什么样没有实物没法聊。`prototype` 用最省力的方式造一个能交互的东西，让人（包括非开发者）驱动它、看它，从而得到可验证的答案。选错分支会浪费整个原型，所以辨题是第一要务。

## 3. 核心心智模型

**问题决定形状，两条分支产出截然不同的产物：**

- **"这逻辑/状态模型对吗？"** → `LOGIC.md`：单个可分享的 HTML，自由点击 + 分页引导走查，把状态机推进到纸上难推的场景，非开发者也能驱动。
- **"这 UI 应该长啥样？"** → `UI.md`：在同一路由上出几个截然不同的 UI 变体，用 URL 参数 + 浮动底栏切换。

**六条普适规则**：① 从第一天起就是 throwaway 且明确标注；② 一行命令就能跑；③ 默认不持久化（内存态，持久化正是它在验证的东西）；④ 跳过打磨（无测试、无多余错误处理、无抽象）；⑤ 每步动作后显示完整状态；⑥ 结束时把验证过的决策折进真代码，原型本身作为一手资料提交到 throwaway 分支并留上下文指针。

## 4. 一次典型运转

1. 辨题：读用户提示/周边代码，必要时问。
2. 走对应分支：逻辑 → 单 HTML 状态机驱动；UI → 多变体单路由。
3. 默认内存态、一行跑起、动作后显示状态。
4. 得到答案后，把结论写进 issue/commit，主分支只保留验证过的决策。

## 5. 何时用 / 何时不用

**用**：想 sanity-check 状态模型/逻辑是否合理，或探索 UI 该长什么样。

**不用**：问题不靠可运行代码也能答（直接讨论）；要做的是正式功能（走 `implement`）。

## 6. 依赖与网络位置

- 是 `ask-matt` 交付链里的可选支线（`handoff → prototype → handoff`）。
- 被 `wayfinder` 的 `prototype` ticket 类型引用（HITL）。
- 附属：`LOGIC.md`、`UI.md`。

## 7. 易错点与坑

- **分支选错**：逻辑问题去做 UI、UI 问题去做逻辑，整个原型白费——辨题优先。
- **原型写得太"真"**：加测试、抽象、持久化，就违背了"快学快弃"。
- **不显式标注 throwaway**：命名要让路人一眼看出这是原型不是生产代码。
- **答案不沉淀**：验证出的决策要折进真代码并留痕，否则白跑。
