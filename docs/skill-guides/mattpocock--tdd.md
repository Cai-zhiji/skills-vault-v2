# tdd

> 测试驱动开发（红→绿循环）：好的测试是什么、测试放哪（接缝）、反模式、循环的规则。

## 1. 一句话理解

`tdd` 是**红→绿循环的参考手册**——它不发明循环，而是定义"什么样的测试值得保留"：测试只通过公共接口验证行为、只写在预先约定的接缝处、避免三个反模式（实现耦合、同义反复、水平切片）。

## 2. 它解决什么问题

TDD 很容易做成"先写一堆测试、再补一堆实现"，结果测试既脆弱又敏感度低，或者断言其实是照抄实现。`tdd` 用四条纪律把这些反模式挡掉，让循环产出的测试真正经得起重构。

## 3. 核心心智模型

**好测试读起来像规格。** "用户可以用有效购物车结账"——它告诉读者"存在什么能力"，且因为不关心内部结构而能活过重构。

**接缝（seam）是测试的唯一合法位置。** 测试只在**预先约定的接缝**处写——动手前先写下要测哪些接缝并和用户确认，没有测试写在未确认的接缝处。接缝形状本身存疑时，用 `codebase-design` 的词汇。

**三个反模式**：

- **实现耦合**：mock 内部协作者、测私有方法、经侧信道验证——重构时行为没变测试却崩。
- **同义反复**：断言用代码同款算法重算期望值（`expect(add(a,b)).toBe(a+b)`），构造上必过、永不失合。期望值必须来自独立事实源（已知字面量、手算样例、spec）。
- **水平切片**：先写全部测试再写全部实现——批量测试验证的是"想象的行为"，测的是形状而非用户可见行为。要改**垂直切片**：一测一实现，每个测试是一颗 tracer bullet，回应上一轮学到的东西。

## 4. 一次典型运转

1. 与用户确认要测的接缝。
2. 红：写一个失败测试（一个 tracer bullet）。
3. 绿：只写足够通过它的最少实现。
4. 回到 2，一个切片一个切片推进。
5. 重构不属于循环——它属于 `code-review` 阶段。

## 5. 何时用 / 何时不用

**用**：想测试先行地构建功能或修 bug、用户提"红绿重构"、或要写集成测试。

**不用**：测试内部实现、已经写完的功能回头补测试（那是另一回事）。

## 6. 依赖与网络位置

- 是 `implement` 的实现方式。
- 用 `codebase-design` 的术语（module/interface/seam）做底座。
- 附属：`tests.md`、`mocking.md`。

## 7. 易错点与坑

- **同义反复断言**：期望值必须独立于实现，否则测试形同虚设。
- **水平切片**：别批量写测试再批量写实现，要垂直切片。
- **在未确认的接缝写测试**：这是硬约束。
- **把重构塞进循环**：红绿循环里不做重构，重构归 `code-review`。
