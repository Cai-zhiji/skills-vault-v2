# Skills Vault 跨平台桌面化需求

## 1. 问题与目标

Skills Vault 当前以 macOS/Linux 本地网站和 Bash 脚本交付。开发启动、后台进程、全局命令、外部工具发现和 Skill 链接都带有 Unix 假设，无法在 Windows 上开箱即用，也没有面向普通用户的安装包。

本次改造要在保留 React 前端、Python 领域服务、本地优先和安全事务模型的前提下，实现：

- macOS、Windows、Linux 的一致开发入口；
- 以 Tauri 桌面应用作为正式日常入口；
- 当前操作系统的一键构建与原生安装包；
- Git 与外部 Skills CLI 缺失时仍可使用核心能力，并获得安装诊断与引导；
- 用户数据与只读应用资源分离，升级应用不覆盖 Vault。

## 2. 已确认产品决定

- Tauri 桌面应用是正式入口，浏览器模式保留作开发、诊断和应急入口。
- React 前端与 Python 领域服务继续复用；不以跨平台为由重写领域核心。
- Git 与外部 Skills CLI 是可选增强依赖，不阻止应用启动。
- 应用提供依赖状态、缺失影响、安装引导和重新检测；受支持的平台可进一步提供受控安装操作。
- 继续遵守 `preview → confirm → apply → transaction → recovery`，依赖安装也不得绕过该边界。
- 本地 Git only，不自动 push，不依赖远程 CI 作为首版构建前提。

## 3. 首批支持范围

### 3.1 操作系统

- macOS 12+：Apple Silicon 为首要构建目标，Intel 架构作为独立产物验证。
- Windows 10/11：原生 x64 为首要构建目标，不要求 WSL。
- Linux：Ubuntu 22.04/24.04 x64 为验收基线，首要产物为 AppImage。

### 3.2 分发产物

- macOS：`.app` 与 `.dmg`。
- Windows：NSIS 安装型 `.exe` 为首要产物，MSI 作为后续企业分发增强。
- Linux：AppImage；Deb 作为后续同阶段增强，不阻塞首个 Linux 产物。

## 4. 用户故事

- 作为开发者，我希望在三种操作系统上使用同一条命令启动桌面开发环境，从而不维护 Bash、PowerShell 和批处理三套流程。
- 作为普通用户，我希望安装后点击应用图标即可使用，从而不必安装 Node.js 或 Python。
- 作为 Windows 用户，我希望不启用开发者模式或管理员符号链接权限也能同步 Skills。
- 作为已有 Vault 用户，我希望选择现有目录并预览迁移影响，从而不丢失原创 Skills、来源、Profile、记录和备份。
- 作为没有 Git 或 Skills CLI 的用户，我希望应用仍能启动并说明哪些能力受限、如何安装以及安装后如何重新检测。
- 作为维护者，我希望在目标操作系统上执行统一打包命令并获得可识别的版本化产物。
- 作为没有任何仓库的新用户，我希望首次启动就能创建一个空 Vault，并从模板创建自己的 Skill。
- 作为已有普通 Skills 仓库的用户，我希望先扫描再选择“作为来源”或“作为我的 Skills”导入，并保留原仓库。
- 作为 Web v2 用户，我希望桌面应用识别当前项目型 Vault，并把事实数据安全迁移到独立用户目录。

## 5. 验收条件

### R1：统一开发入口

- 当开发者在受支持系统执行 `npm run dev` 时，系统应检测构建依赖、启动 Tauri、React 与 Python 开发进程，并在主进程退出后清理子进程。
- 当默认端口被占用时，开发入口应选择可用端口或返回可执行的诊断，不得静默连接错误服务。
- 当路径包含空格或非 ASCII 字符时，开发、测试与打包命令应保持可用。

### R2：桌面启动与生命周期

- 当用户启动已安装应用时，系统应在不依赖系统 Node.js 或 Python 的情况下打开桌面窗口并启动配套 Python sidecar。
- 当桌面窗口退出且没有后台任务需要继续时，系统应正常关闭 sidecar，不遗留进程或固定端口占用。
- 当已有应用实例运行时，再次启动应聚焦现有实例或安全退出，不得启动两个写入同一 Vault 的实例。

### R3：应用资源与用户数据

- 当桌面应用首次启动时，系统应在可写用户目录创建新 Vault，或允许用户选择已有 Vault。
- 当应用升级或重新安装时，系统不得覆盖、删除或静默迁移用户 Vault。
- 当用户选择旧项目型 Vault 时，系统应先生成迁移预览和备份，再执行结构升级并记录事务。
- 当应用以开发模式运行时，系统应继续允许显式指定仓库根目录作为 Vault。

### R4：平台目录与 Skill 部署

- 当系统计算 Codex、Claude Code 或 Lux Desktop 的目标目录时，应通过平台适配器返回路径，不得依赖硬编码路径分隔符判断平台。
- 当部署到 Lux Desktop 时，应把 `SKILL.md` 映射为 `~/.lux/skills/<name>.md`，保留同名资源目录，并在存在且通过 schema 校验的 watcher 配置时映射为 `<name>.json`。
- 当旧 Profile 缺少 `platform` 或 `platforms` 时，应保持 Codex + Claude Code 语义，不得因升级静默部署到 Lux。
- 当 Skill 名称可能逃逸平台目录或命中 Windows 保留设备名时，Catalog 与部署计划都应拒绝该条目。
- 当平台适配器选择目录链接策略且能力检测通过时，系统应使用受管链接部署 Skill。
- 当 Windows 链接权限不可用时，系统应使用受管复制，并记录来源、内容指纹、部署类型和恢复信息。
- 当受管复制在目标端被用户修改时，重新同步或移除前应阻塞覆盖、展示差异并要求确认。

### R5：可选外部依赖

- 当 Git 或外部 Skills CLI 缺失时，系统应继续提供本地扫描、浏览、说明、Profile 和记录能力。
- 当某项操作依赖缺失工具时，系统应在预览或执行前返回结构化的 `dependency_missing` 错误及影响范围。
- 当用户进入依赖中心时，系统应显示检测路径、版本、可用能力、官方安装入口和“重新检测”。
- 当系统提供自动安装时，应只使用已声明的可信安装提供者，并执行预览、用户确认、结果记录和失败恢复说明。

### R6：本地 API 安全

- 当 Tauri 启动 sidecar 时，sidecar 应绑定随机回环端口并建立仅本次进程有效的会话凭证。
- 当请求缺少有效会话凭证或来源不属于当前桌面应用时，sidecar 应拒绝写操作。
- 当应用处于浏览器诊断模式时，现有本机 Host/Origin 与 Preview token 保护应继续生效。

### R7：打包与发布

- 当维护者在目标操作系统执行 `npm run package` 时，系统应构建前端、冻结 Python sidecar、运行 Tauri bundler 并将产物放入统一的版本化输出目录。
- 当构建环境缺少 Node.js、Rust、Python 或平台打包组件时，打包命令应在写入产物前给出明确缺失项。
- 当产物未签名或未公证时，构建结果应明确标记为内部测试版本，不得被描述为公开发布就绪。
- 当需要其他操作系统产物时，维护者应在对应系统或虚拟机中独立构建，不假设 PyInstaller 可以跨操作系统编译。

### R8：测试矩阵

- 当提交跨平台改动时，Python 测试应覆盖 POSIX 链接、Windows 受管复制、路径安全、回滚和迁移。
- 当提交桌面壳改动时，测试应覆盖 sidecar 握手、随机端口、单实例、异常退出和缺失依赖。
- 当生成安装包时，每个目标系统应完成安装、首次启动、选择 Vault、同步 Skill、恢复和卸载后数据保留的烟测。

### R9：首次启动与仓库导入

- 当用户没有 Vault 时，首次启动向导应允许选择位置并预览创建最小 Vault 结构；Git 缺失不得阻止创建。
- 当用户在新 Vault 中创建原创 Skill 时，系统应预览名称、目标路径、平台范围和模板文件，确认后写入 `my-skills/<name>/` 并记录事务。
- 当用户选择已有目录时，系统应只读识别“完整 Skills Vault、普通 Git Skills 仓库、普通 Skills 文件夹或无效目录”，不得在识别阶段写入。
- 当用户导入普通 Skills 仓库时，系统应允许把仓库作为受管来源导入，或把选中的 Skills 复制为用户原创内容。
- 当导入发现同名、无效 `SKILL.md`、嵌套 Skill 或目标路径冲突时，系统应在 Preview 中逐项显示并阻止静默覆盖。
- 当用户迁移当前 Web v2 Vault 时，系统应复制事实数据和来源仓库、重新生成 Catalog，并把旧事务与备份标记为历史数据；运行 PID、日志、Preview token 和旧安装状态不得直接成为新 Vault 的活动状态。
- 当 Web v2 迁移完成时，系统应比较迁移前后 Skill 数量和内容指纹，并单独预览 Codex / Claude Code / Lux Desktop 部署目标的重指向。
- 当迁移任一步骤失败时，新 Vault 应回滚到未完成状态，旧 Vault 和原有平台链接应保持不变。

## 6. 非目标

- 首阶段不提供云端账户、跨设备同步或多人协作。
- 首阶段不提供自动在线升级；先保证可重复打包、版本识别和数据兼容。
- 首阶段不内嵌完整 Git 或 Node.js 运行时；是否内嵌需基于依赖中心的实际使用数据另行决策。
- 首阶段不支持移动端，也不承诺所有 Linux 发行版。
- 不自动获取管理员权限，不静默执行系统包管理器命令。
- 不在导入或迁移完成后自动删除、移动、归档旧仓库。

## 7. 完成定义

在 macOS、Windows 和 Ubuntu 的干净环境中，用户可以安装并打开 Skills Vault；没有 Git/Skills CLI 时应用可正常进入并清楚显示受限能力；安装依赖后可重新检测；至少一个 Skill 能经过 Preview/Apply 部署到 Codex、Claude Code 或 Lux Desktop，并可从备份恢复；所有用户数据在应用升级和卸载后保持可恢复。
