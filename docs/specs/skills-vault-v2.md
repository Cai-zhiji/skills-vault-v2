# Skills Vault v2 产品规格（决策地图阶段）

## 1. Problem Statement

现有 Skills Vault 已经能扫描、比较、筛选、安装和更新多个来源的 Agent Skills，但主要能力分散在命令行、静态网页、菜单和多层弹窗中。普通使用者必须理解 Catalog、Profile、安装链接和来源状态才能完成日常操作；网站还不能完整覆盖“本地文件变化 → Catalog → 平台生效”的闭环。

v2 需要把网站变成主要工作台，让用户先看到真实状态，再在同一上下文中完成管理动作，同时继续保护本地文件、上游仓库和平台安装目录。

## 2. Solution

构建一个本地优先的 React Web 应用，以 Skills、来源和记录作为一级信息架构，并用“同步轨”表达本地文件、Catalog、Codex 与 Claude Code 之间的状态关系。

界面使用 shadcn/ui 作为可访问组件基础，使用 Tailwind CSS 和项目级设计令牌形成专属视觉语言。所有危险或批量写操作延续“预览 → 确认 → 应用 → 事务记录 → 可恢复”的模型；CLI 只保留启动、诊断、自动化和应急能力。

## 3. User Stories

### 浏览与理解

- US-01：作为维护多个 Agent Skills 的用户，我希望打开网站就能看见整体同步状态，从而知道现在最需要处理什么。
- US-02：作为用户，我希望按名称、来源、兼容平台、启用状态和健康状态筛选 Skills，从而快速定位对象。
- US-03：作为用户，我希望在详情中看到说明、依赖、风险、来源、版本和平台状态，从而无需跳转多处拼接信息。
- US-04：作为键盘用户，我希望用统一搜索或命令入口打开页面和常用动作，从而减少鼠标路径。

### 本地 Skills

- US-05：作为原创 Skill 作者，我希望把包含 `SKILL.md` 的目录加入本地后能在网站扫描发现，从而不必记忆 CLI 命令。
- US-06：作为用户，我希望扫描前知道 Catalog 是否落后，扫描后看到新增、变化、缺失、警告和冲突，从而理解真实变化。
- US-07：作为用户，我希望无效 Skill 保留在磁盘，并看到精确路径和修复建议，从而不会因扫描丢失成果。

### 启用与同步

- US-08：作为同时使用 Codex 与 Claude Code 的用户，我希望为 Skill 选择共享、仅 Codex、仅 Claude 或关闭，从而维护不同平台集合。
- US-09：作为用户，我希望界面明确区分“已保存选择”和“已经安装到平台”，从而不会误以为配置已生效。
- US-10：作为用户，我希望安装前看到新增、移除、替换和保留项，并能在异常时恢复备份，从而安全同步平台目录。
- US-11：作为用户，我希望同名冲突在应用前被阻止并提供比较入口，从而明确选择唯一实现。

### 来源维护

- US-12：作为用户，我希望查看每个来源的版本、信任、许可、锁定、脏文件和更新状态，从而判断是否安全操作。
- US-13：作为用户，我希望可更新来源与被阻塞来源分开处理，从而让一个脏仓库不会阻止其他安全更新。
- US-14：作为用户，我希望系统绝不自动清理、暂存、提交或覆盖来源中的本地改动，从而保留工作成果。
- US-15：作为用户，我希望添加、暂停、恢复或删除来源时先看到影响范围，从而避免意外改变大量 Skills。

### 反馈与恢复

- US-16：作为用户，我希望长耗时操作持续显示当前阶段，从而知道系统仍在工作。
- US-17：作为用户，我希望相关按钮在操作期间立即锁定，同一凭证不能重复消费，从而避免重复提交。
- US-18：作为用户，我希望失败信息持续存在，并说明原因、未发生的改动和下一步，从而能够恢复。
- US-19：作为用户，我希望查看事务和备份记录并发起恢复预览，从而追踪和撤销受管变化。

### 响应式与可访问性

- US-20：作为窄屏用户，我希望主任务仍完整可达，从而能在较小窗口中检查和处理状态。
- US-21：作为键盘或辅助技术用户，我希望焦点、标签、Dialog、Sheet 和状态反馈遵循可访问语义，从而独立完成操作。
- US-22：作为减少动态效果的用户，我希望界面尊重 `prefers-reduced-motion`，从而避免不必要动画。

## 4. Implementation Decisions

### 已确认

- 前端使用 React、shadcn/ui 与 Tailwind CSS。
- 网站是主要产品入口；CLI 仅承担启动、诊断、自动化和应急维护。
- 系统保持本地优先，首发不依赖云端账户或远程数据库。
- 核心领域模型继续区分事实源、可重建 Catalog、用户选择和平台实际安装状态。
- 批量或破坏性写操作继续使用一次性预览凭证和事务记录。
- 页面一级信息架构以 Skills、来源和记录为候选基线，最终结构由对应决策票确认。
- 视觉采用“本地仓库工作台”方向，签名元素是同步轨；不复制参考品牌的营销页面。
- 旧项目目录仅作为研究和迁移来源，v2 在新目录中独立初始化。

### 尚待决定

- React 使用 Vite SPA、React Router framework 或其他本地交付方式。
- 后端继续使用 Python 服务层，还是建立新的边界与适配层。
- 旧项目数据、用户内容和运行时状态采用复制、引用还是迁移命令。
- API 的最终资源模型、错误结构、异步任务与取消语义。
- 首发功能边界、延后功能和 CLI 精简范围。
- 打包、后台启动、升级和跨平台支持范围。

这些问题的唯一事实源位于 `docs/wayfinder/tickets/`，本规格不提前替它们作答。

## 5. Testing Decisions

### 已确认

- 领域服务与文件操作需要自动化测试，避免 UI 测试代替核心安全验证。
- API 契约需要覆盖预览过期、重复消费、脏来源、部分成功/阻塞和可恢复错误。
- 浏览器测试需要覆盖页面加载、筛选、扫描、启用、更新阻塞、操作轨、Dialog/Sheet 焦点和窄屏布局。
- 视觉验收需要在真实浏览器中检查桌面与窄屏，并确认无控制台错误。
- 任何迁移过程必须支持只读预检，并使用旧项目副本或测试夹具验证。

### 尚待决定

- 单元、集成与端到端测试的具体工具组合。
- 测试接缝是领域服务、HTTP API 还是进程级应用外壳。
- macOS 专属行为与跨平台行为的测试边界。

## 6. Out of Scope

- 首发不建设云端账户、多用户协作或远程数据库。
- 不改变 `SKILL.md` 的上游格式规范。
- 不自动修改来源仓库中的用户文件或 Git 历史。
- 不在项目初始化阶段实现页面、API 或迁移脚本。
- 不承诺 v1 的每个入口原样保留；先由产品边界决策票确认价值。
- 不把参考设计的品牌资产、专有字体或页面结构直接复制到本项目。
